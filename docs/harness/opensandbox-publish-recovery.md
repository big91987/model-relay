## 正式操作者确认与报告

仅在同版固定门禁和独立 QA 放行后进入 approval 安全点。协调者依据已有授权完成该安全点规定的控制核验，再通过正式 decision 确认；这些行为的完成结论只能来自平台真实回执，不能冒称用户本人点击。approval 不是命令执行，不用命令日志接口冒充其确认结果；下游 report 直接取得平台保存的确认上下文，缺失时明确阻塞，不臆造授权。

report 生成 `harness-output/report.json`，包含 title、body、files。正文覆盖相对真实 main 的全部实际变更、旧候选继承关系及本轮测试/QA/确认边界，并附同版 QA 原文。files 必须是本版需暂存的具体仓库相对文件，最多100项，每项不超过5MiB，不列目录、依赖、凭据或未保存文件。已提交旧材料不需重复塞入 files；必要本轮证据必须实际保存并列入，未发布材料不得伪装远端链接。

### 同 Run、同节点恢复与材料保持

平台确认可恢复后，授权协调者通过正式 resume 入口接续当前 Run 的原 approval 节点，而不是新建节点、重新 prepare 或重启 Run。恢复前后核对 Run ID、冻结 revision、节点与执行关系、HEAD 和未提交候选清单/逐文件 SHA-256，确认首轮快照、QA 拒绝和修订版、固定测试原层文件仍在且字节未变；预期新增的操作者回执另列映射，不把它们误认为候选变更。

恢复结果以平台状态及正式回执为准。已接受的 handoff 不重交，已保存的确认不重做；报告或发布结果未知时先核对原报告、分支和 PR，避免重复创建。材料丢失、身份不符、同节点接续失败或状态不明时停在当前节点，用原生 wait_for_input 的 blocked 说明实际影响、证据和下一步，由平台责任角色处理；不擅自改冻结准备、凭据或资源限额求绿。确认材料保持及控制验证完成后，才由授权操作者正式 decision；report 直接使用平台保存的确认结果，不把 approval 当命令日志读取。
