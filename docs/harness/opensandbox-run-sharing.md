## 停止、恢复与环境释放

### 安全停顿与取消的区别

当前原生工具已明确支持 `handoff` 和 `wait_for_input`：handoff 接受后当前角色结束，不再改文件；需要澄清或真实外部阻塞时，wait_for_input 写明具体问题、证据和下一步，等待新输入接续同一会话。这是角色交接或等待，不是整个 Run 的停止，也不证明环境已释放。

本任务把最终 QA 通过后的正式人工确认节点作为操作者验证安全停顿点。停顿前须已保存本版文件、清单及测试/QA 原文，没有仍在修改这些文件的角色；停止/接续操作由已授权协调者通过平台正式入口执行并保存实际回执。本轮研发没有调用平台停止、取消、恢复或释放操作，没有可据以证明这些操作的按钮/API 回执，因此不编造操作接口或点击记录。该行为目前 **未验**，后续只能称“授权操作者确认”，不能称用户本人点击。

停止或取消正在运行的测试与在安全停顿点等待不是同一件事。若涉及测试取消，必须核验实际执行退出、所属进程组结束、临时候选及端口清理；项目 runner 的短预算子进程回归和执行 9 的清理证据不替代平台停止/接续验证。命令回执的 sandbox.stopped 字段、context deadline exceeded 或节点结束都不能单独证明 Owner stop、整个 Run 取消或环境释放。

### 接续身份与去重

未知停止/接续结果先核对原 Run、节点、执行身份及正式留存输出，必要时用 read_command_output 的原 seq/offset 读取到 EOF，区分 accepted、运行中、完成、取消、超时和证据不足。没有确定结果时不重放副作用命令，不新建下一节点、不重启 Run，不以新的执行掩盖旧失败。

在环境仍可用且平台允许接续的前提下，沿用当前 Run、冻结 revision2、固定 HEAD 和现有未提交候选；先读取既有文件，核验完整清单与源码摘要，再从实际停顿位置继续。已接受的 handoff 不再次提交相同交接；已形成的报告/PR 或未知发布结果由对应平台角色先核对已有产物及字节身份，不重复创建。审批安全停顿点的停止/接续是否确实保持同 Run、同版文件且没有重复节点/报告/PR，须由操作者留下前后证据；本轮仅说明核对要求，不宣称去重已通过。

释放前由平台责任角色确认必要材料已经可访问保存：冻结身份白名单、固定基点和可达历史、当前候选及完整清单、首轮快照、历次失败/撤回/纠正记录、完整测试日志及 state、独立 QA 拒绝/复核原文、操作者确认回执、最终报告和 PR 字节核验结果（若已产生）。未产生的材料标记未完成，不伪造或复制凭据、会话、数据库、依赖目录及含秘密的运行证据。归档摘要应绑定真实文件，而不只是聊天中描述的路径；保存材料不等于验证成功。
