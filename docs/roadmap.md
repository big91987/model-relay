## 研发与发布规则

- 产品路线图定义公共阶段目标；[基础契约](releases/v0.1.0.md) 持续回归，最新 Issue 及其 Run PRD 定义当前增强范围。
- 需求→可评审交互设计→研发（维护 Trellis 真实规范）→固定 `make verify` 项目测试→独立 QA（版本验收 Skill）→草稿 PR→维护者核对并合并→正式测试部署→部署后浏览器体验核验，各阶段按真实回执报告。M2–M4 不提前变成当前前置项。
- 文档批准类普通选择按已授权的自动推荐推进，必要澄清和高风险权限操作单独处理。
- 用户已授权本目标维护者在核对独立 QA 后自主完成测试仓 PR 合并与正式测试部署，无需等待用户另行合并或重新批准；阶段 Agent 如实交付草稿 PR，不自行越过节点职责，也不预报未来发布成功。授权不包括平台源仓 PR 合并。阶段“完成”、草稿 PR 和测试通过不等于版本发布。
- 状态必须链接真实 Issue／Run／PR。源码未产生、外部联调未进行时如实标明，不因文档完整而宣称可用。
- Run 需求与证据按 Run 根保存，不覆盖历史；项目级契约原位维护。发现平台问题交维护源修复，经原 manifest 升级复验，不向产品放平台补丁。
