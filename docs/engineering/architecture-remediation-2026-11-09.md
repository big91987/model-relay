# Model Relay 完整架构治理：职责与验证结果

上一轮只提取了路由、金额计算和调用测试页，管理操作、运行状态、供应商协议及其他页面仍集中在 `relay`。本轮沿用 `codex/model-relay-architecture-pass` 分支，按上一轮工具报告的四个遗留问题继续整改，使每项业务操作、状态和协议都有明确归属，并保留现有产品行为。

本轮不增加业务功能，不切换框架，不迁移数据库，也不合并或部署。下文分别呈现结构变化、工具判断及运行验证；结构重构的回归不等同于独立产品 QA 或真实供应商验收。

## 四个问题实际改到了哪里

| 原报告问题 | 改造前 | 改造后及具体对象 |
| --- | --- | --- |
| HTTP、业务规则与 SQL 混合 | `relay` 中的管理处理函数同时做解码、权限判断、事务和响应 | `httpconsole.Controller` 负责 HTTP；`identity`、`apikey`、`catalog`、`finance` 拥有业务操作；`admission` 拥有原子接纳与预留；`records` 拥有请求和尝试记录；`reporting` 拥有管理读模型；`installation` 拥有安装、升级与恢复 |
| Server 汇集会话、限速和检查状态 | Server 直接管理多个共享状态集合 | `sessions.Manager` 管会话、登录/邀请限速与密码计算槽；`configstate.Coordinator` 管配置代次、成功证据和连接检查；`routing.Engine` 管路由状态；`app.Server` 负责组装 |
| 网关生命周期混合供应商协议 | 网关流程中实现 HTTP、普通 JSON 和 SSE 解析 | `upstream.PrepareChat` 准备请求，`Client.Send` 发送，响应和流解析器验证协议；`relay.Gateway` 保留取消、超时、输出提交、尝试和重试 |
| 前端业务集中在两个入口 | 工作台与旧版入口包含页面业务、请求和状态 | 15 个功能目录各自拥有页面请求、状态和退出清理；`workspace.js`、`app.js` 组装会话、范围、导航与通用编辑器；`shared` 保存通用传输、格式化和生命周期 |

`internal/relay` 从 **27 个生产 Go 文件、262743 字节**变为 **6 个文件、31809 字节**，剩余文件均为网关流程。文件数用于定位实际变化，不作为质量评分。完整数量及路径见[结构对照](evidence/architecture-2026-11-09/structure.json)。

```text

  app/             组装与公共 HTTP 边界
  httpconsole/     管理 HTTP 适配
  identity/        登录、租户、成员、邀请

  reporting/       人员与租户范围内的管理读模型
  relay/           推理请求生命周期

  accounting/      金额与资源纯计算
```

## 拆分后的操作边界

- **Key 轮换**：HTTP 解码后调用 `apikey.Service.Rotate`；权限、租户状态、修订、密钥代次、幂等和审计在同一操作事务内处理。旧版 Key 修改也由服务协调锁、提交和运行状态发布，控制器不再补做发布。
- **请求接纳与结算**：`admission.Admit` 在同一事务内完成鉴权、幂等回执、价格快照、额度检查及预留；价格读取归 `finance.PriceAt` 和 `CurrentModelRate`。`records.Finish` 与启动恢复共同使用 `finance.Settle`，不把结算拆成另一次独立提交。
- **管理读取**：`reporting.Tenants` 在一个事务快照中组合身份与财务摘要；`LegacyOverview` 拥有整个旧版总览读模型，只对已确认过期的成功证据返回清理指示。查询未完成时保留当前证据。
- **调用供应商**：准备成功后再记录派发可能性并发送；选择证据和派发序列保持事务内顺序。输出提交后不能重放；结果持久化成功后才采用延迟样本，旧配置结果不能污染当前代次。
- **前端离开页面**：功能取消自己的请求、拒绝过期结果、清理临时密钥。额度展示归 limits，通用标签与值格式化归 shared，旧版各功能自行处理字段定位。

## 工具报告与复核

检查器保持 **0.4.1**，安装清单逐文件摘要无漂移。仍使用原来的 **11 项**模型检查要求，没有降低门槛或改写检查器。`architecture.json` 覆盖 116 个生产源文件，声明能力包、状态包及前端公开入口：能力服务禁止 HTTP；HTTP 适配和组装禁止 SQL；纯规则与状态包同时禁止 HTTP/SQL；前端功能不能相互读取内部实现。

确定规则最终为 `conformant`。隔离副本中注入 routing→HTTP、功能→功能依赖，均被拒绝，真实生产代码未注入探针。见[依赖反向探针](evidence/architecture-2026-11-09/dependency-probes.json)。上一轮四项遗留已按上表处理；各轮复扫中接受的进一步问题也已整改，包括报表权限谓词归属、只读查询锁范围、重复名称校验、旧版配置发布、租户读模型、价格读取和总览读取。

最终模型仍提出以下四个候选建议。独立源码复核认为它们不构成阻止本轮交付的架构缺陷，保留原文及处理依据，不将结果写成“模型零发现”。

| 模型候选 | 复核结论与依据 |
| --- | --- |
| reporting 用字符串替换适配查询别名 | 可选可读性改进。权限决策只有 `reportScope` 一处；替换在同包私有查询中复用固定别名，值仍使用绑定参数，未发现第二套授权规则或范围泄漏 |
| 通用协议与硬预留字段限制应合并 | 不采纳。通用协议接受范围和可证明资源上界是两项不同策略；协议新增字段不能自动扩大硬预留范围。移除后者会使原来应拒绝的 tools 请求通过，真实 HTTP 反例已验证 |
| schema 分支应改为独立兼容实现类型 | 不采纳。分支对应当前明确支持、入口已校验的模式，差异在能力内局部处理；没有独立状态或生命周期需要额外包装类型。DDL 和升级仍只有 installation 拥有 |
| 启动恢复与普通请求完成的 SQL 重复 | 不采纳。独占启动恢复与正常完成是不同状态迁移，installation 按声明拥有恢复；共享财务不变量已经通过 `finance.Settle` 复用 |

更早模型提出的“统一邀请展示和有效时钟”“删除取得锁后的重复时钟采样”同样不采纳：前者会改变原有展示/审计语义，后者会遗漏排队期间经过的期限。原有时钟倒退时邀请列表可能显示待处理而接受已拒绝的展示局限保持，不能据此声称修好了它。见[时钟处理依据](evidence/architecture-2026-11-09/clock-disposition.json)和[真实 HTTP 反例](evidence/architecture-2026-11-09/policy-counterexamples.json)。

模型复扫存在格式和引用错误。原拒收结果保持 `incomplete`；最后一轮两处检查依据引用不匹配，针对同一冻结材料进行仅引用更正，再由标准入口校验，不修改检查器、不删除发现、不改变判断。具体报告、摘要和调用记录见[证据说明](evidence/architecture-2026-11-09/README.md)。模型接受报告不等于其每条整改建议都正确。

## 验证与保留限制

原有 **118 个 Go 测试入口**全部保留并移入实际归属包；历史基线与业务断言保持。见[测试迁移清单](evidence/architecture-2026-11-09/test-migration.json)。历史复制夹具仅适配新包引用，进程超时用例增加启动余量，不删超时和子进程回收断言。

旧代次观察的三个隔离删守卫变体均在预期断言失败；保留守卫时通过。额度预留和锁后时钟采样也分别做真实 HTTP 对照/删保护实验，全部得到预期结果。这些是架构重构的行为保护，不能替代产品验收。

最终通过受支持的隔离 **`make verify`**，退出码 0，总耗时 **936.550 秒**。初始没有 node_modules 或 npm 缓存，按锁文件安装依赖；执行前后源码及候选内容未变化，结束后自有进程组和临时目录均已清理。详见[原始状态回执](evidence/architecture-2026-11-09/verify-state.json)、[结果摘要](evidence/architecture-2026-11-09/verification-summary.json)和[完整日志](evidence/architecture-2026-11-09/verify.log)。
