# 管理台运行服务版本：需求与验收基线

## 1. 目标与证据

让团队管理员在登录后的概览直接确认当前运行实例报告的版本，辅助判断测试环境升级结果，无需把静态页面标签当作运行版本。

需求来源为 Issue #9 的原始任务、平台送达的澄清结果及 `docs/workflow/task.md` 的已确认行为。展示位置、取值及不可用行为已由用户确认，本次不重复访谈。本文替换此前 v0.1 整体产品需求基线作为本次局部功能基线；此前内容可从 Git 历史追溯，既有 design、delivery、qa、pr 文档及日志仍属历史任务，不代表本次完成证据。产品背景仍遵循 `docs/product-brief.md`、`docs/roadmap.md` 和 `docs/releases/v0.1.0.md`，不扩展里程碑范围。

仓库证据：现有管理台概览没有运行版本，顶部为静态「v0.1 · 团队模型网关」；现有 `/healthz` 成功响应含运行配置的 `version`，服务启动传入构建版本，默认 `dev`。健康检查可因存储故障返回失败，不能假定始终成功。版本值能证明实例自报版本，不额外保证构建标记准确、所有实例一致或部署成功。

成功标准：下列全部 P0 AC 有对应回归和真实验证证据，固定入口 `make verify` 的结果交独立 QA 核验；最终经平台回写原 Issue、由 Connector 交付草稿 PR，不部署。需求就绪不等于实现、测试或 QA 通过。

## 2. 用户、范围与业务规则

用户故事：作为测试环境的团队管理员，我希望登录管理台后在概览看到当前实例报告的版本，以确认升级后运行的是哪一版；版本不可用时仍可继续管理，并在后续重试时恢复展示。

最小闭环：管理员按已有登录流程进入概览 → 查看当前版本或「版本未知」→ 按需继续其他管理操作 → 重新进入概览或刷新页面后重新获取。运行版本来自现有服务健康接口，管理员无需创建或配置版本记录；升级由原有运行流程负责，本任务只读取其结果。退出登录后不展示运行版本。应用调用方及供应商不参与该闭环。

已确认的 P0 范围与规则：

- 仅在登录后的「概览」新增只读运行版本展示，不在登录前或全局顶部新增运行版本。
- 唯一来源为现有 `/healthz.version` 原始值，包括 `dev`；不从静态标签、源码版本或 GitHub 推断，不加版本前缀或替换含义。
- 请求失败、字段缺失或为空时显示准确文案「版本未知」，不阻塞其他管理操作，不将上次成功版本冒充本次获取结果。
- 每次重新进入概览或刷新页面后重新获取；接口恢复后可恢复显示返回的版本。
- 只读，沿用现有管理台和健康接口，不调用供应商、不更改管理配置或业务数据。

推荐默认值（低风险补充，直接采用）：

- 展示标签使用「运行版本」，沿用现有概览视觉风格，不新增页面或用户权限。
- 不增加定时轮询、自动生成请求、手动刷新专用按钮或版本持久化；沿用用户已确认的重入与页面刷新重试。
- 无法解析的响应、非字符串及仅含空白的版本按不可用处理；有效非空字符串按原始文本显示，不作 HTML 执行。检测空白不改变有效值的显示内容。
- 版本获取尚未完成时可显示局部加载状态，但不得延迟其他管理能力的可用性；等待上限及具体交互由设计落实。

## 3. 验收标准（全部 P0）

| ID | 场景与可观察结果 | 验证方式 |
|---|---|---|
| AC-01 | 未登录时不展示新增运行版本；登录或恢复有效会话进入概览后可见「运行版本」；切换其他页面或退出登录后不出现新增运行版本展示。 | 实际 Go 服务的管理台旅程及界面回归。 |
| AC-02 | 健康接口返回有效版本字符串时，概览显示该原始文本；分别覆盖发布样式字符串及 `dev`，不得回退到静态 v0.1 标签。 | 自动回归核对响应与显示值；真实服务核对 `/healthz.version` 与 UI 一致。 |
| AC-03 | 分别模拟网络失败、非成功 HTTP 状态、字段缺失及空字符串，均显示「版本未知」；不可解析响应、非字符串、仅空白值同样降级，不显示旧版本。 | 对各输入独立进行确定性回归，保留失败路径证据。 |
| AC-04 | 版本请求失败或未完成时，其他健康的管理接口与导航仍可正常使用；不因版本请求失败触发退出登录或掩盖原有管理结果。 | 隔离版本请求异常，验证概览其余信息与至少一次其他管理页读取；不把全服务存储故障造成的不可用归因于版本展示。 |
| AC-05 | 首次失败显示「版本未知」，接口恢复后离开再进入概览重新请求并显示新版本；刷新页面并在有效登录状态进入概览也重新获取。先成功再失败时不得继续显示上次值。 | 分别覆盖重入、刷新、失败恢复与成功后失败；核对请求次数及显示结果。 |
| AC-06 | 退出登录、离开概览或较新读取完成后，旧请求的迟到结果不使隐藏页面重新出现或覆盖当前读取结果。 | 延迟响应及连续导航的确定性回归。 |
| AC-07 | 版本文本仅作只读文本展示；含标记的字符串不会执行；版本读取不写入配置或业务数据、不发起供应商请求。 | 文本安全回归、请求记录与代码审查；实际服务旅程不使用供应商。 |
| AC-08 | 针对本次代码有新增回归；运行固定入口 `make verify`，保留真实结果和失败证据；独立 QA 核对本次代码版本、成功与失败覆盖。通过后由平台回写原 Issue 并经 Connector 提供草稿 PR，无部署操作。 | 开发验证回执、独立 QA 记录、平台交付回执。未执行、失败或受限均如实记录，不计作通过。 |

职责：开发提供实现与回归及固定入口真实回执；独立 QA 核验 AC 和证据一致性；平台 Hook 负责原 Issue 沟通，Connector 负责 Git 发布和草稿 PR。需求节点只固化基线，不执行这些后续动作。

## 4. 非目标、依赖与关键风险

- 非目标：登录前版本展示、顶部动态版本改造、版本编辑、升级/部署控制、发布历史或 GitHub 查询、供应商联调、多实例一致性验证、新接口或数据库、整体管理台重构。
- 依赖：现有登录、概览导航和健康接口；不新增外部服务、凭据、付费调用或权限。原 Issue 内容及评论由平台送达，本节点不自行读取或写入 GitHub。
- 风险：请求阻塞、迟到响应和旧值残留可能误导升级判断；AC-03～06 要求局部降级与恢复。服务自报版本可能为 `dev` 或构建时未正确标记，应照实显示，不用静态标签补齐。
- 风险：健康接口存储故障可能同时影响其他管理接口。非阻塞承诺仅指版本展示不额外阻塞，不能承诺故障服务的其他操作成功。
- 实际 UI 验证必须启动 Go 服务；静态预览不是后端联通证据。测试使用隔离临时数据与端口，不接触用户上游或修改数据凑通过。
- 未决关键方向：无。视觉布局、等待边界及回归组织留给设计，不在本节点选择底层组件。出现权限扩大、付费使用或不可逆操作时重新澄清；普通细节继续采用自动推荐。

## 5. G1 自查

- 结论与状态：`Ready for Architecture`。依据用户已确认的关键行为及项目明确的自动推荐授权，可交接设计，无需重复阶段审批；此结论仅为需求就绪。
- 已满足：目标与来源可追踪；管理员最小闭环、版本来源与首次可用路径明确；正常、未知、重试、退出及迟到响应均有可观察 AC；非目标和验证责任明确。
- 裁剪：局部只读展示，不新增运营模式或核心资产管理；不生成组织级 PRD、额外业务架构文档、原型或 PoC。
- 非阻塞缺口：布局及等待边界由设计确定；自动化证据由实现与 QA 提供，本节点未运行 `make verify`，未声明任何功能验收通过。
- 阻塞项与待用户裁决事项：无。
- 带入设计的约束：只在登录后概览、健康接口原值（含 `dev`）、准确未知文案、独立降级、重入/刷新重试、文本安全及迟到结果隔离、零供应商调用；保持现有服务与权限边界，不部署。
